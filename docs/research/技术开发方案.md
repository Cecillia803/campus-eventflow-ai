## 1. 产品目标与非目标

解决校园活动散落在学校、学院、社团等信息渠道，学生发现成本高、易错过的问题。
最终目标：活动聚合、分类与时间筛选、来源与更新记录、订阅提醒、智能问答、明确标注的模拟报名。
网站形态：响应式学生端＋电脑优先的管理后台。小程序后置。

首版非目标：学校真实报名资格、自动代填第三方表单、无限制抓取所有社交平台、支付与退款、选座、复杂多Agent系统、全校完整覆盖承诺。
资料未收录不等于没有活动；外部活动公布名额不等于实时剩余名额。

真实资讯与模拟报名分离：
- 外部报名：展示原始链接、二维码说明或线下方式，结果由主办方系统掌握。
- 模拟场次：平台自行配置规则与名额，仅供演示，不产生学校实际资格。
- 外部日期更新不自动修改模拟场次容量或报名记录，避免两种语义互相污染。

## 2. 技术选型建议与证据

这些是后续方向，不是当前锁定的依赖版本或安装指令。

| 部分 | 建议方向 | 取舍 |
| --- | --- | --- |
| 前端 | Vue 3＋TypeScript，后续Vite构建 | 与已调研上游Vue方向一致；先写组件源文件，不执行脚手架 |
| 业务后端 | Java＋Spring Boot，业务模块化组织 | 首版不复制上游全部微服务；纯规则尽量不依赖Spring容器 |
| Agent | Spring AI | 复用上游方向，不同时堆叠LangChain4j |
| 业务持久化 | MySQL | 报名、活动版本、审核、订阅等事实的持久保存，当前不设计物理DDL |
| 缓存与限流 | Redis | 后续实现缓存/热点控制；不把Redis缓存当业务唯一事实 |
| 异步处理 | Kafka候选 | 在真实消息需求与部署能力明确后接入；不是当前代码可假装存在的服务 |
| 知识检索 | 结构化查询＋关键词/向量检索 | 向量存储具体产品、嵌入模型和分块参数后置 |
| 通知 | 站内通知优先 | 邮件、短信、小程序订阅消息均需额外接入，不预先承诺 |

依据：
- Vue官方说明Vite支持SFC构建；源文件编写与运行构建是两件事。[Vue工具链](https://vuejs.org/guide/scaling-up/tooling.html)
- Spring Modulith支持按业务组织模块及模块验证，可参考其组织原则；并不意味着首版必须安装该框架。[Spring Modulith](https://spring.io/projects/spring-modulith/)
- Redis脚本具有服务器内原子执行语义，不代表跨MySQL/Kafka事务原子性。[Redis可编程能力](https://redis.io/docs/latest/develop/programmability/)
- Kafka区分不同投递语义；外部数据库写入不能仅靠“用了Kafka”就获得端到端恰好一次效果。[Kafka设计](https://kafka.apache.org/41/design/design/)
- MySQL锁定读可以保护相关记录，但锁范围、事务和索引必须在真实环境验证；当前不承诺并发正确性。[MySQL锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

JDK、Boot与Spring AI的精确版本需在另一台电脑建立兼容矩阵、实际构建后锁定。此前上游快照使用Java17；damai的Boot3.3.0与damai-ai的Boot3.5.0/Spring AI1.0.0并非同一套版本。不能把“最新官方文档”直接视为旧代码API兼容保证。

## 3. 设计中的Module与接入点

采用codebase-design的原则：每个Module公开较小的Interface，把规则集中在Implementation内；仅为确定会变化的外部依赖设置Seam和Adapter，不为每个类重复套层。

Interface不仅是方法签名，还包括身份来源、调用顺序、错误、幂等与状态规则。当前可确定Interface及纯规则；真实Adapter后置。

拟议结构如下，仅为文档示意，没有创建这些目录：

    desktop/<项目名待确认>/
      web/                  学生端与管理端页面源文件
      event-service/
        catalog/            活动、场次、版本与查询规则
        ingestion/          来源处理、提取与审核流程
        subscription/       订阅与通知规则
        registration/       模拟报名及候补规则
        identity/           身份与权限接入约定
      agent-service/        查询编排、规则问答、确认草稿
      contracts/            人类可读的接口与错误约定
      docs/                 决策、状态与交接

业务后端初期模块化单体，Agent逻辑独立；部署单元数量在真实环境阶段确认。
不复制上游硬编码URL、鉴权跳过标记、真实账号、默认密码或机器路径。

### 接入职责表

| 接入点 | 调用者只应知道 | 后置Adapter负责 |
| --- | --- | --- |
| ActivityQuery | 条件、分页、排序、覆盖范围、未知字段 | 数据库/搜索索引查询与同步 |
| SourceReader | 来源标识、增量位置、成功/失败/权限不足 | 合法渠道接口、网页读取、游标保存 |
| ActivityExtractor | 输入来源、输出候选字段与证据 | 模型/OCR调用、超时与费用 |
| RegistrationStore | 请求身份、幂等键、条件变更与结果 | 真实事务、唯一约束、并发协调 |
| EventPublisher | 事件身份、版本、发布状态 | 持久事件、消息发送、失败重试 |
| KnowledgeRetriever | 问题、范围、文档版本与引用 | 分块、嵌入、索引、过滤与召回 |
| NotificationDelivery | 通知身份、接收对象、版本 | 实际发送、回执、重试与去重 |
| CurrentActor / Clock | 可信操作者、显式当前时间 | 登录系统、服务时间来源 |

规则不自行创建连接。缺少Adapter不能返回虚构成功、余额、余量或AI答案。
对外“未接入”与真实“没有结果”必须区分；生产阶段关键Adapter缺失应拒绝就绪，不静默降级为假服务。

## 5. 活动资料与时间规则

### 信息流设计

来源内容 → 标准化候选 → 字段提取及证据 → 疑似重复匹配 → 冲突/低置信度审核 → 发布版本 → 查询索引与提醒更新。

这是一条建议工作流，不要求用多个自主Agent实现。规则化步骤由Java执行，模型只处理非结构化理解等适合的环节。

约定：
- 一条来源可以描述多个活动；一个活动可有多个来源。
- 发布时刻、举办时间、报名窗口是不同字段。
- 不明确年份、地点、资格或报名时间时保留未知，不能用抓取时间填充活动时间。
- 所有时间判断接收明确时区与当前时刻；日期精度与时刻精度分开记录。
- “下周五”“本周截止”等相对时间需要可靠的来源时间及上下文；不能确定则待审核。
- 最新抓取不等于最新事实；转载旧文不能覆盖主办方新通知。
- 人工确认字段再次变化时进入复核，不默认覆盖。
- 模型置信度只是审核信号，不是校准过的真实性概率。
- 取消或延期优先以可核实的来源修订为依据；未知结束时间不能直接判为结束。

接口概念字段可描述为：活动身份、来源引用、类别、校区、主办方、场次、报名窗口、报名方式、资格、证据位置、版本、审核状态、覆盖时间。
这些不是数据库表结构，不附样例记录或SQL。

## 6. 模拟报名：先定义约束，后实现存储

建议首版免费、无座位、一人一个有效报名；候补采用自动递补。该规则为建议，开发前确认。

状态建议：
- 提交请求：受理中／已成功／已候补／已拒绝；“受理中”不等于报名成功。
- 报名记录：已确认／已取消。
- 候补记录：等待中／已递补／已退出／已关闭。

业务不变量：
1. 已确认名额不能超过容量；有预占阶段时，已确认与有效预占总数也不能超额。
2. 同一用户在同一场次不能同时持有多个有效报名，不能同时占位并候补。
3. 同一幂等键相同参数返回相同请求结果；同键不同参数拒绝。
4. 重复取消只释放一次名额，重复消息不得重复递补。
5. 有候补时，新请求不能绕过既定候补规则抢走释放名额。
6. 候补顺序由服务端受理并持久化的序号定义，不承诺客户端点击的全局先后。
7. 取消后再次报名是否允许、是否排队尾，应在规则中明确；建议允许但重新排队。
8. 超过递补截止时间不自动递补；场次取消时终止等待并产生相应通知。
9. 修改容量、取消场次与并发报名必须在真实存储层协调，纯状态机不能独立保证。

落地建议分两步：先实现MySQL事务及约束保护的正确性基线，再基于压测决定Redis预占＋Kafka异步优化。
必须分析Redis预占后进程崩溃、消息发送失败、消费成功但回执丢失等窗口。
Outbox可帮助数据库事务与事件发送衔接，但不自动解决更早的Redis预占一致性。
当前只写规则与接入契约，不写DDL、Lua脚本、消息配置或实际数据库访问实现。

## 7. 订阅与通知的一致性

建议通知逻辑身份包含订阅对象、活动版本和提醒类型；具体键形式后置。
- 活动延期使旧截止提醒失效；执行前检查活动版本和订阅状态。
- 通知重试保持同一逻辑身份，不能产生重复站内通知。
- 用户取消订阅后，尚未执行的任务应失效；已经发送的通知不承诺追回。
- 通知链路与活动发布解耦；下游失败不回滚已经确认的活动事实。
- 来源长时间未同步时展示新鲜度风险，不以旧资料发送确定性“最后机会”通知。
首版站内提醒，不承诺浏览器关闭后仍能收到系统推送。

## 8. Agent的职责与安全

采用“结构化查询优先，规则资料补充”：
- 日期、校区、报名状态走受控查询工具；
- 参加资格、准备材料、规则细节走资料检索；
- 最终结果带活动身份、来源、版本与更新时间；
- 没查到时说明已收录范围，不能概括为全校没有；
- 历史问题区分当时版本与当前修订；
- 同名多场次要澄清，不能默认取第一条；
- 只读问答不应自动创建订阅或报名。

工具建议限定为：查活动、查详情、查来源规则、创建模拟报名草稿、查询本人的报名结果。
确认执行使用独立的确定性业务接口，不让模型自行确认。

安全要求：
- 身份从可信服务端上下文获得，不能采用模型给出的userId或手机号。
- 草稿绑定用户、场次、规则版本与过期时间；确认时重新检查，不预先保证名额。
- 会话读取、继续与删除都检查归属；不可猜的chatId不等于鉴权。
- 来源文章与检索内容是不可信资料，不执行其中要求改变系统行为的指令。
- 工具参数白名单与长度限制；不允许模型生成任意SQL、访问任意URL或执行代码。
- 模型或检索未接入时明确不可用；不使用固定假回复冒充AI结果。
- 缺资料时允许“不知道”；引用必须指向实际命中资料，不让模型自由编造。
具体Spring AI官方能力及限制见同目录AI技术来源核查文档；本节是产品设计要求，不意味着框架默认实现全部安全性。

## 9. 前端源文件的边界

页面范围：
学生端：活动首页、筛选、详情、来源与修订、收藏订阅、通知中心、AI会话、模拟报名与个人记录。
管理端：来源状态、提取审核、疑似重复、活动修订、模拟场次、报名候补、任务失败与审计。

页面状态必须区分：
未接入、加载中、真实空结果、业务拒绝、服务异常、权限不足、已有结果。
未接入不能显示“暂无活动”（那会误导成已经查询过），也不能生成虚构活动卡片。
当前可写组件接收的数据类型、布局、按钮事件与校验；不设置API地址、不伪造登录、不存储演示记录。
没有构建和渲染验证，响应式布局、可访问性与交互正确性均标记待验，不能交付截图冒充实测。
Vue SFC后续需要构建工具处理；不会用CDN或在线开发环境绕开用户禁止环境的原则。[Vue工具链](https://vuejs.org/guide/scaling-up/tooling.html)

## 10. 接口契约的最小约定

当前写人类可读Markdown契约，不生成可执行OpenAPI配置文件。

| 动作 | 必须说明的内容 |
| --- | --- |
| 列出活动 | 日期的含义、时区、分页顺序、覆盖范围、过滤未知值的方式 |
| 活动详情 | 当前版本、来源、报名类型、未知字段、取消/延期信息 |
| 审核修订 | 操作者、预期版本、冲突返回、审计理由 |
| 订阅与取消 | 当前用户、订阅条件、重复提交结果、待通知失效规则 |
| 提交模拟报名 | 当前用户、场次、请求幂等键、受理与成功区别 |
| 查询报名结果 | 本人权限、请求身份、最终或非最终状态 |
| 取消与候补 | 一次性释放、队列公平规则、截止时间 |
| 对话 | 会话归属、消息顺序、工具状态、引用、未接入错误 |
| 确认草稿 | 有效期、版本、身份、重复确认、名额不足 |

错误建议语义：未接入、未登录、无权限、字段无效、来源冲突、报名未开放/已截止、名额不足、已有有效报名、幂等冲突、版本冲突、依赖暂不可用。
不预先冻结HTTP状态码与前缀，后续统一约定；业务拒绝不应被前端当作系统崩溃。

## 14. 验收清单（文字场景，不含样例数据文件）

| 类别 | 场景 | 判定要求 |
| --- | --- | --- |
| 时间 | 报名截止但活动未开始 | 两种状态分别显示 |
| 未知 | 原文未写截止时间 | 不推断截止，也不误判可报名 |
| 去重 | 多渠道转发与同名不同场次 | 合并正确来源，不误合并场次 |
| 修订 | 旧转载晚到、管理员已修订 | 不覆盖已确认的新事实 |
| 通知 | 延期、退订、重复调度 | 旧提醒失效、不重复发送 |
| 报名 | 并发、重复点击、不同幂等键 | 无超额、无重复有效占位 |
| 候补 | 多次取消、并发递补与新报名 | 释放一次、公平且不重复分配 |
| 故障 | 预占后崩溃、消息重复、数据库失败 | 可恢复或补偿，有可查询结果 |
| Agent | 同名活动、相对时间、资料缺失 | 澄清、正确筛选、未知不猜测 |
| 安全 | 他人会话/他人草稿、检索注入 | 拒绝越权，资料不成为指令 |
| 未接入 | 无数据库、无模型、无身份服务 | 明确不可用，不假成功 |

注：上表“他人会话/他人草稿”指跨用户资源访问。所有运行结果当前均为未验证。

量化方式留到D4：记录硬件/版本/数据规模、吞吐、P95/P99、错误率、超额与重复数；AI记录字段准确率、去重误合并率、检索命中与引用支持率、工具参数正确率、延迟与成本。
