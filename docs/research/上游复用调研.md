# 校园活动预约与 AI 助手：damai / damai-ai 复用调研

日期：2026-09-15。用途：辅助范围与方案决策，不是开发实施或上线验收。
本次只下载研究快照、阅读源码和保存调研文档，没有改动灵裁妙搭项目，没有创建或推送 GitHub 仓库。

## 结论

两个项目值得作为参考和可选择复用的基础，但不能直接将“演出票务”改名为“校园预约”。
damai 的强项是库存竞争与异步订单链路；damai-ai 的强项是已成形的 Spring AI 工具与检索链路。
建议围绕一个产品建立业务后端与 Agent 两个边界，把个人贡献集中在可靠报名、候补递补、可控 AI 操作和评测。
不必完整复制上游微服务规模，也不必同时引入 Spring AI 和 LangChain4j。

## 研究范围与证据

静态阅读，不曾完整部署、调用真实大模型或进行压测。因此不保证上游性能宣传或整体可靠性。

## 2. 不能忽略的改造成本

### “不选座”仍然依赖座位

Lua 的 type=2 分支读取可售座位 HVALS，解码并寻找相邻座位，再执行锁座。
订单参数还含票档、观演人、座位、金额等字段。因此免费一人一个名额不是关闭选座按钮就完成。
建议明确 Activity（活动）—Session（场次）—Registration（报名），库存只针对场次。
证据见上面的库存脚本与 ProgramOrderService。

### Redis成功、MQ成功、数据库成功是三个不同阶段

ProgramOrderService 的异步路径等待发送回调后返回订单号，并不是等消费者数据库事务完成。
发送回调失败有回补处理，但不能因此推导进程崩溃、网络异常、重复消息等都已可靠覆盖。
其中 CountDownLatch.await() 未显式设超时，也需要核查。
应设计可查询的报名结果、持久请求记录、重试与补偿，并测试Redis预占与持久化之间的失败窗口。
Outbox可以解决数据库事务与事件发布衔接，但单独添加Outbox并不会自动解决之前Redis预占的原子性。

### 消费端不能直接当作完备可靠消息方案

CreateOrderConsumer 对超过5秒的消息放弃建单并回补；异常在该方法中捕获后只记录日志。
不能指望这种方法自动触发异常重试；实际还需结合容器确认与错误处理配置。
其注释明确把部分补偿、对账、实时监控能力指向Pro版本。
校园集中报名应重新决定排队时限和公平策略，不能直接保留5秒废单规则。

证据：[Kafka消费实现](https://github.com/java-up-up/damai/blob/9fc3fbbdc6db8e20e872251a18757d49bb7d0586/damai-server/damai-order-service/src/main/java/com/damai/service/kafka/CreateOrderConsumer.java)。

### 防重复下单不等于防重复报名

订单号去重、Redis重复执行标记并不直接保证一个学生在一个场次只有一个有效报名。
需区分：
1. 同一请求重试：返回同一结果；
2. 用户发多个不同请求：不能重复占名额；
3. 用户取消后再次报名：按明确规则允许或禁止。
数据库约束、事务与状态机需要配套设计，而不是只加分布式锁。

### 取消支付订单不等于候补递补

上游取消入口约束未支付订单；校园免费报名则需要取消已确认报名。
本次在damai-server与sql/cloud检索候补/waitlist/outbox未发现对应实现。
建议实现持久候补队列、稳定排序、一次性释放/分配和并发竞争处理。
先选“自动递补”或“通知后限时确认”一种规则，不要首版同时实现两套。

## 3. 环境体量

damai 根POM为Java17、Spring Boot3.3.0、Spring Cloud2023.0.2，包含MyBatis Plus、Redisson等模块。
节目服务配置直接涉及ShardingSphere数据源、Redis、Nacos、Kafka、Elasticsearch。
它不是只接上MySQL和Redis就必然完整运行的轻量应用。

建议首版保留业务需要的MySQL、Redis；异步报名阶段保留Kafka。
分库分表、服务注册发现、复杂灰度和支付先不纳入首版目标。
删去依赖需要同步重构调用、配置与数据访问，并非直接删除几个目录。

证据：[根POM](https://github.com/java-up-up/damai/blob/9fc3fbbdc6db8e20e872251a18757d49bb7d0586/pom.xml)；[节目服务配置](https://github.com/java-up-up/damai/blob/9fc3fbbdc6db8e20e872251a18757d49bb7d0586/damai-server/damai-program-service/src/main/resources/application.yml)。

## 4. 建议的项目边界（方案，不是当前实现）

- event-service：账号权限、活动发布、场次名额、报名取消、候补、状态查询、可靠事件。
- agent-service：活动理解与筛选、规则检索、工具调用、会话、操作确认草案、评测。
- web：学生页面、组织者后台、AI聊天与确认卡片。
- docs / deploy / tests：设计决策、迁移与种子脚本、环境模板、运行手册、测试与压测。

业务后端可以先做模块化单体，Agent独立服务。一个仓库容纳两个服务，不强行统一全部上游版本。
Agent不能直接写报名表或扣Redis名额，普通按钮和AI确认都调用同一套业务接口。
没有AI或模型超时时，用户仍能直接报名。

## 5. 建议的首版范围

保留：免费、无选座、一人一名额、管理员/CSV录入、活动查询、定点开放报名、取消、候补、AI查找与规则解释。
后置：真实支付退款、选座、公众号/抖音自动采集、跨校身份认证、大规模分库分表、多Agent协作。

区分“资讯”与“本平台可报名活动”：导入一篇学校公众号文章不代表本平台能控制该活动名额。
资讯可提供原链接；只有主办方在平台配置发布的活动才进入本平台报名链路。

示例：周五19点开放的200人讲座。
AI根据时间兴趣查场次、解释规则 → 用户确认 → 后端校验身份和报名窗口 → 原子争抢名额 → 查询报名结果。
取消后按规则递补。余量与报名资格始终实时查询业务接口，不从可能过期的RAG文档决定。

## 6. 简历可讲的实际成果与验收

后端重点：
- 并发报名不超额、重复请求不重复占位；
- 取消与候补并发时不重复分配；
- MQ重复/延迟、数据库失败、进程重启后的最终状态恢复；
- 在写明硬件、请求模型和数据规模的压测中报告吞吐、P95/P99、成功率及一致性检查。

Agent重点：
- 结构化需求到工具调用，参数缺失追问；
- 服务端身份绑定与写操作确认；
- 规则回答引用来源，库存走实时接口；
- 固定评测集测检索命中、工具参数正确率、未确认写操作拦截、越权会话访问和超时降级。

不应把现成的Lua、RAG、聊天记忆或工具调用包装为个人原创；说明复用来源，突出修改、测试和取舍。
本次尚无实测QPS和模型效果数据，不能写成已实现成果。

## 7. 复用与开发顺序

1. 先核对并跑通上游参考链路；这一步后续在主要开发电脑执行。
2. 定义校园领域、首版范围、接口和失败状态，形成自己的项目结构。
3. 完成直接按钮报名闭环与测试，再引入异步优化。
4. 加候补、补偿与压测，建立可验证的后端贡献。
5. 接AI只读工具与规则检索，再做确认后报名，最后补评测。
6. 数据库迁移、演示数据和环境模板版本化；真实凭据不提交Git。

选择性复用并不等于完全重写：保留能解释、能测试且符合领域的组件，其余以明确边界适配。
damai仓库含Apache-2.0许可；使用时保留相关许可与来源说明，另核对每个被复用仓库及依赖的许可。

### 必须修正前面过于简化的理解

1. 不是所有查询都通过damai业务API：ProgramCall搜索/推荐直接使用Easy-ES查询Elasticsearch；详情、票档、用户和下单另走HTTP。
2. 上游AI下单常量调用的是create/v1，不应误以为默认AI已经使用异步高并发下单链路。
3. AI根POM为Spring Boot3.5.0、Spring AI1.0.0，与damai Boot3.3.0不同。可以分别构建部署，不强行把POM合并。
4. 默认向量库是内存SimpleVectorStore，启动加载Markdown并embedding，不是已有持久化向量服务。
5. 混合检索代码只有向量结果非空才融合；若向量结果为空，已有关键词结果会被丢弃。这是静态可定位、适合配测试验证的改进点。
6. recommendation结构化演示未见传入真实候选库，不宜直接作为可信活动推荐。

### 最有价值的交叉贡献：受控报名Agent

当前createOrder接收模型提供的手机号等参数，通过手机号找用户，按搜索首条节目、价格等选择目标。
OrderCall携带no_verify:true请求头，所读方法未转发当前登录用户身份。
提示词要求与用户确认，但所查工具/DTO/Controller中未见持久确认状态或专用确认凭证。
这不是完整部署安全审计，但足以说明不能原样沿用到校园账号操作。

建议把链路改为：
查询明确场次 → 生成绑定当前用户的报名草稿 → 页面展示确认卡片 → 用户点击确认 → Java重新校验并幂等执行。
草稿绑定场次、规则版本、有效期和服务端用户身份。模型不能通过提供另一个手机号变更操作者。
余量不足或场次变更必须返回业务结果，而不是模型自行重试一个新报名。

证据：[下单HTTP调用](https://github.com/java-up-up/damai-ai/blob/8e16ac3ef51d7ea8ad29347db8b164037886b89a/damai-core-service/src/main/java/org/javaup/ai/ai/function/call/OrderCall.java)；[工具](https://github.com/java-up-up/damai-ai/blob/8e16ac3ef51d7ea8ad29347db8b164037886b89a/damai-core-service/src/main/java/org/javaup/ai/ai/function/AiProgram.java)。

### 会话隔离不能只相信chatId

ProgramController接受客户端chatId；ChatTypeHistoryController按type/chatId读取与删除记录。
所查链路内未见当前用户归属校验，不能排除部署环境外部鉴权；校园版仍应在服务端按用户检查每个会话。
会话ID难猜不等于权限控制。

证据：[聊天接口](https://github.com/java-up-up/damai-ai/blob/8e16ac3ef51d7ea8ad29347db8b164037886b89a/damai-core-service/src/main/java/org/javaup/ai/cotroller/ProgramController.java)；
[历史接口](https://github.com/java-up-up/damai-ai/blob/8e16ac3ef51d7ea8ad29347db8b164037886b89a/damai-core-service/src/main/java/org/javaup/ai/cotroller/ChatTypeHistoryController.java)。

### 不应该包装成原创的内容

Spring AI接入、@Tool、RAG、RRF、基础聊天记忆、结构化输出及token统计上游均已有。
可以形成个人贡献的是：领域适配、确认与鉴权、检索缺陷修复、引用与版本治理、隔离和评测，以及和可靠报名链路的结合。
本次检索未发现系统化评测集；发现的RagAiTest是主源码下的手动检索输出组件，不等于完整自动化验收。

## 9. 最终取舍

值得做，但应把项目定位为“基于开源票务与AI助手改造的校园活动预约系统”，而非原创票务底座。
首版的三个支柱：
1. 可靠报名：限额、幂等、可查询结果、异常恢复；
2. 公平候补：取消与递补规则及并发正确性；
3. 受控Agent：真实查询、规则依据、用户确认、身份隔离。

先把这三个支柱做扎实，再考虑扫码签到、活动资讯采集和AI运维。
